# OpenSpec roadmap

Future IDs are planning references. Allocate each type-local sequence only when checking the current proposal set. Each accepted implementation depends on the preceding evidence relevant to it.

| Milestone | Planned change | Evidence needed |
| --- | --- | --- |
| Foundation | Repository governance and research baseline | CraftAtlas audit, repository checks, branch and review settings |
| Client diagnostic | `feat001-forever-diagnostics` | Safe field projection, session and lifecycle timing, reload, recipient coverage and native component probes |
| Capture foundation | Addon lifecycle, safe damage-meter adapter and metric registry | Observed session finality, identity and restricted field contract |
| Dungeon and encounters | Instance tracker, party revisions, attempts and completion | Manual and queued test runs, wipes, reset and reload overlap |
| Data and history | Model, aggregation, versioned persistence and migrations | Deduplication, retention, unknowns, restart and migration fixtures |
| Native UI | Core native controls and original report window | Forever component probe, visual acceptance at multiple scales, taint checks |
| Timeline | Pooled chart, filters, legend, segments and interval interaction | Verified data resolution and aggregated-segment boundary tests |
| Reports | Summary, per-player and encounter details, history and settings | Totals, coverage, UI navigation and localization |
| Follow-up | Comparisons and personal trends, performance and visual audit | Multiple real runs, representative memory and UI fixtures |
| Distribution | Deterministic ZIP, SemVer, owner-only release and compatibility checks | License and creator notice included, policy compliance, installable artifact tests |

The initial milestone combines API and UI source research because both depend on the same pinned Forever build. The diagnostic implementation is the first runtime change. A narrower release or re-scoped timeline is possible if the client exposes only a subset of the desired data.
